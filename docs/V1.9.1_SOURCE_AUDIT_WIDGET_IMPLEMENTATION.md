## Verified application architecture

- Single Java `Activity`: `tw.kangyuan.tvlauncher.MainActivity`.
- Home UI is assembled programmatically in `buildHome()` using a vertical `LinearLayout`.
- App tiles are rendered in a `GridView` with 4 columns for large cards and 6 for small cards.
- App discovery queries both `LEANBACK_LAUNCHER` and `LAUNCHER` activities.
- Existing folders, app ordering, wallpaper URI, recent apps, and language are stored in `SharedPreferences`; folder records are JSON.
- Existing wallpaper selection uses legacy `startActivityForResult` request code 701.
- Manifest currently declares the HOME / DEFAULT / LEANBACK_LAUNCHER activity and optional leanback/touchscreen features. No widget host code or launcher widget-host receiver is present.
- No AndroidX dependencies are declared in `app/build.gradle`; implementation can use platform AppWidget APIs without adding a dependency.

## Widget implementation design for this baseline

Use native platform classes available at API 26:
- `AppWidgetManager`
- `AppWidgetHost`
- `AppWidgetHostView`
- `AppWidgetProviderInfo`
- `RemoteViews`

Keep the implementation in the existing Java Activity initially to avoid introducing an unnecessary architecture migration. Create a dedicated widget area as a sibling section above the existing App grid; never place widgets inside app-card cells and never change the 4 / 6 app-card column rules.

### Lifecycle
- Create a stable host ID and instantiate the host once per Activity instance.
- Start listening when the Activity is active; stop listening when it is paused/stopped according to the host lifecycle.
- Allocate widget IDs only when the user selects a provider.
- Bind using the system permission flow; if binding is denied or canceled, delete the allocated ID and retain the launcher state.
- Launch provider configuration only when the provider declares a valid configuration Activity.
- Persist only widget IDs plus layout metadata in a versioned preference record; do not persist View objects.
- Restore IDs on Activity creation, validate provider availability, and remove stale IDs safely.
- Delete the host ID when a widget is removed.

### UI / remote behavior
- Add a clear **小工具** / **新增小工具** entry to the home edit/menu flow.
- Enumerate providers through `AppWidgetManager.getInstalledProviders()`; never show a fabricated list.
- Present provider labels and optional preview/icon; handle absent previews and invalid providers.
- Place each widget in its own bounded host container with D-pad focus behavior.
- Keep focus traversal predictable between toolbar, widgets, and the app GridView.
- Initial version should support adding, configuring, displaying, removing, and basic layout placement. Resizing / drag rearrangement should be enabled only when provider resize metadata and the host layout can support it reliably; do not promise arbitrary resize on all widgets.

## Compatibility and constraints

- This project supports API 26 and above, not every Android version ever released.
- Android TV / Google TV firmware may omit, restrict, or customize widget hosting. Detect runtime capability and degrade gracefully.
- A third-party widget may be designed only for touch devices or phone aspect ratios. Do not promise that every installed provider is TV-usable.
- Keep targetSdk 28 and current build configuration unchanged during the first implementation pass unless a separate security / compatibility review justifies a change.
- Do not require Google Play services.

## Regression requirements

- Large app cards remain 4 columns; small app cards remain 6 columns.
- App discovery / launching, folders, wallpaper, language, recent apps, HDMI entry, settings, and remote navigation remain intact.
- A device with no providers, denied binding, missing configuration Activity, provider uninstall, or widget restore failure must not crash the launcher.
- Test at least API 26 and a newer Android TV / Google TV environment before release.

## Not yet verified

- Physical Android TV OEM widget-host behavior.
- Actual installed third-party widget providers and their D-pad usability.
- Whether each provider's configuration Activity is usable on TV.
- Resizing behavior across different providers and display densities.
